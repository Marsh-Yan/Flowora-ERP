# ADR-0002：Flowora ERP 2.0 演进策略

## 状态

Accepted

## 背景

Flowora ERP 1.0 已以 Java 25、Spring Boot、Vue 3、MySQL、Redis 和模块化单体完成发布。2.0 需要在保留既有数据和关键查询能力的同时，引入多组织、细粒度权限、可配置工作流、进阶库存、正式财务和升级工具。

## 决策

### 保留现有技术栈与模块化单体

2.0 继续使用现有 Monorepo 和模块化单体。只有在模块边界、数据所有权和运行压力得到实际证据后，才考虑拆分服务。

### API 采用增量 v2

- 新增和升级后的业务能力通过 `/api/v2` 暴露；
- v1 认证、会话与无损读取在 2.0 保持兼容；
- 在对应 v2 写能力和前端迁移完成前，不提前关闭 v1 写入；
- 最终切换后，v1 业务写统一返回 HTTP 426，错误体包含升级提示和 requestId；
- `/api/v2/system/version` 作为客户端与部署诊断的版本协商入口。

### 数据库迁移只向前追加

- 已发布的 V1–V9 永久冻结；
- 2.0 的首个数据库变更从 V10 开始；
- 禁止修改、重排或复用已发布版本号；
- 迁移必须同时在空库和 1.0 样本库验证；
- 大表变更采用扩展、回填、切换、清理的分步方式。

### 阶段门禁

M0–M5 每阶段使用独立分支和 Pull Request。阶段必须完成测试、迁移说明、验收证据和风险说明；用户审核通过后才能进入下一阶段。

## 影响

### 正面影响

- 1.0 数据和调用方具有明确兼容路径；
- 数据库历史受到自动化保护；
- 各阶段变更规模可控，便于审核和回滚；
- 避免在 2.0 初期引入微服务部署复杂度。

### 代价

- 过渡期需要同时维护 v1 与 v2；
- 兼容测试和迁移演练会增加工程量；
- 部分领域需要适配层，直到前端和调用方全部迁移。
