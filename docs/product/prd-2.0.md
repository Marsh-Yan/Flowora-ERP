## 2. 产品概述与需求分析

### 2.1 1.0 已有基线

1.0 已经具备：

- Vue 3 + TypeScript 的中英文 ERP 工作台，以及 Spring Boot 模块化单体 API。
- 登录会话、粗粒度角色、组织字段、统一错误、请求追踪、审计事件和幂等保护。
- 客户、供应商、商品、仓库、币种、汇率、税率和科目等主数据。
- 固定规则审批、任务箱、站内通知、评论和活动时间线。
- 采购申请、采购订单、采购入库、调拨、盘点、库存调整和移动加权平均成本。
- 销售报价、销售订单、部分出库、应收依据和分次收款。
- 总账、凭证、会计期间、应收应付、收付款、试算平衡和基础财务报表。
- 项目、里程碑、任务、工时、费用、预算和可计费依据。
- 全局搜索、经营看板、CSV、打印、演示种子数据和发布验证入口。

### 2.2 从演示版到真实试用版的关键差距

| 差距 | 1.0 现状 | 2.0 必须解决的问题 |
| --- | --- | --- |
| 身份 | 内存演示账号，数据库用户仅作审计关系 | 持久化用户、密码生命周期、会话治理、可选 MFA |
| 组织 | 固定单组织，组织字段仅作隔离预留 | 多组织成员关系、当前组织切换、跨组织只读汇总 |
| 权限 | 六类粗粒度角色 | 资源动作权限、数据范围、岗位角色和职责分离 |
| 单据 | 部分界面按单行演示 | 正式多行单据、行级来源、税、折扣与部分处理 |
| 可逆性 | 缺少退货、退款、贷项和完整冲销 | 所有已过账结果通过引用原单的反向业务纠正 |
| 库存 | 仓库 + 商品余额 | 库位、批次、序列号、保质期、预留与完整追溯 |
| 财务 | 订单/收货直接形成应收应付依据 | 独立发票、三单匹配、银行对账、预算和汇兑 |
| 工作流 | 固定阈值和单层任务 | 版本化模板、条件、串并行步骤、委托与超时 |
| 协作 | 纯文本评论和站内通知 | 附件、@成员、邮件通知、失败重试和权限继承 |
| 交付 | 本地演示，无生产运维方案 | 标准私有部署、监控、备份、恢复和升级预演 |
| 质量 | 自动化以单元/API 测试为主 | 真实依赖集成测试、端到端、迁移、并发与恢复测试 |

### 2.3 已确认的产品决策

- 2.0 服务贸易批发和项目型服务企业，不转向制造业产品。
- 采用单租户私有部署；一个实例只服务一个客户集团，但允许多个法人组织。
- 财务做到管理会计增强，不承诺中国或其他国家的法定报税合规。
- 暂不建设电商、物流、支付等外部业务连接器。
- 仓储做到进阶库存，不建设波次、路径优化和自动补货策略等完整 WMS。
- 提供响应式 Web、附件、@成员和邮件通知，不建设原生 App 或客户门户。
- 必须支持从未经修改的 1.0 数据库原地升级到 2.0。
- 继续采用模块化单体，不以微服务拆分作为 2.0 目标。

### 2.4 产品原则

1. **源单可追溯**：任何履约、开票、收付款、退货、贷项和冲销都必须引用来源单据及来源行。
2. **已过账结果不可篡改**：错误通过反向单据、更正或冲销修复，不直接更新历史流水。
3. **当前组织唯一**：用户一次只在一个活动组织中执行写操作，组织 ID 由服务端会话确定。
4. **权限默认拒绝**：没有显式权限即不可见、不可操作；跨组织汇总使用独立只读权限。
5. **状态分维度表达**：生命周期、审批、履约、开票和结算状态分别维护，避免组合状态歧义。
6. **异步副作用可恢复**：邮件、通知和文件后处理失败不得回滚已提交的核心业务，也不得静默丢失。
7. **国际化语义一致**：服务端返回稳定代码、标准时间和定点数，界面负责语言与地区格式。
8. **升级优先于重建**：数据库变更必须考虑 1.0 数据映射、核对、兼容窗口和恢复方案。

### 2.5 需求依据与假设

本 PRD 依据 1.0 仓库现状、1.0 发布限制、既有项目章程以及成熟 ERP 的公开官方资料编制。批次/序列号的端到端追溯、库存预留、贷项反向分录、多组织活动上下文、项目工时开票与项目盈利是成熟产品中的常见能力，但 Flowora 的具体交互仍需通过试点用户验证。

当前没有真实企业访谈、历史使用数据或法务/财税机构背书，因此：

- 本文不将产品假设包装为市场统计结论。
- 税务、凭证、数据保存年限等规则均为管理口径，不代表特定司法辖区合规。
- 试点阶段必须记录任务成功率、异常路径、权限配置难度和业务人员反馈，再决定 2.x 深化方向。

## 3. 用户、场景与成功标准

### 3.1 目标企业

- 有 20–300 名内部使用者的贸易、批发、分销或项目型服务企业。
- 拥有 1–10 个法人组织、多个部门和仓库，但不需要多租户平台运营。
- 希望统一销售、采购、库存、财务和项目数据，能够接受私有部署和配置式实施。
- 不以生产制造、复杂自动化仓储或特定国家税务申报为首要诉求。

### 3.2 标准岗位

| 岗位 | 主要任务 |
| --- | --- |
| 实例管理员 | 初始化实例、组织、邮件、存储、备份、安全和全局配置 |
| 组织管理员 | 管理本组织成员、部门、角色、编号、审批模板和业务设置 |
| 销售专员 / 销售经理 | 报价、订单、信用检查、履约跟进、退货和销售分析 |
| 采购专员 / 采购经理 | 采购申请、订单、收货跟进、退货和供应商分析 |
| 仓库操作员 / 仓库经理 | 收货、上架、预留、出库、调拨、盘点和批次追溯 |
| 应收会计 / 应付会计 | 销售发票、供应商发票、贷项、账龄和往来核销 |
| 出纳 | 收款、付款、退款、银行流水和对账 |
| 总账会计 / 财务经理 | 科目、期间、凭证、汇兑、预算、结账和财务报表 |
| 项目成员 / 项目经理 | 项目、任务、工时、费用、里程碑、计费和毛利管理 |
| 审批人 | 按流程处理本人或受委托的审批任务 |
| 管理层 | 查看跨模块和授权组织的经营汇总，处理高风险审批 |
| 审计员 | 只读访问授权范围内的单据、凭证、权限变化和审计链 |

标准岗位只作为默认角色模板。组织管理员可以复制模板并组合权限，但不能突破实例级安全约束。

### 3.3 核心用户任务

1. 销售人员从多行报价创建订单，系统检查信用和可用库存，仓库分批交付，财务按交付或服务依据开票并分次收款。
2. 采购人员从申请创建订单，仓库按库位和批次收货，财务完成供应商发票三单匹配并付款。
3. 客户或供应商发生退货时，业务、库存、应收应付和总账形成一致的反向链路。
4. 仓库可以回答“某一批次从哪里来、当前在哪里、发给了谁”，并阻止过期或冻结库存正常出库。
5. 项目经理把工时、费用、采购和库存消耗汇总为项目成本，并把可计费依据生成草稿销售发票。
6. 管理员用配置而不是代码建立审批模板，并能审计每次模板发布和实例决策。
7. 实例管理员能够完成部署、升级、监控、备份和恢复演练。

### 3.4 版本目标

- 支持多个组织在同一实例中安全独立运行核心业务。
- 补齐贸易主链的反向流程和正式财务单据。
- 使库存数量、预留、追溯维度、成本和总账保持一致。
- 使项目收入、成本、计费和毛利可从来源单据追溯。
- 让审批和内部协作可配置、可审计、可恢复。
- 让 1.0 数据能够可重复、可核对地升级到 2.0。
- 提供达到试点使用要求的安全、性能、可观测性与运维能力。

### 3.5 可量化成功标准

| 类别 | 2.0 成功标准 |
| --- | --- |
| 业务完整性 | 正向和反向销售、采购、库存、财务、项目五类主链全部通过端到端验收 |
| 数据隔离 | 自动化跨组织越权用例 100% 被拒绝，试点期无跨组织数据泄漏 |
| 财务正确性 | 所有已过账凭证借贷平衡；库存、往来和总账控制数核对无差异 |
| 可追溯性 | 关键业务结果 100% 可追溯到来源单据、来源行、操作者和请求 ID |
| 升级 | 标准 1.0 快照升级成功率 100%，控制数核对通过且不重复记账 |
| 可靠性 | 邮件、通知等异步失败可观测、可重试，业务事务无静默丢失 |
| 性能 | 基准规模下常用查询 P95 ≤ 800 ms，普通写操作 P95 ≤ 1.5 s |
| 运维 | 完成数据库与附件联合恢复演练，达到默认 RPO 24 小时、RTO 4 小时 |
| 体验 | 核心任务在桌面端完整可用，审批、查询、盘点和轻量录入在手机浏览器可用 |
| 国际化 | P0/P1 界面无硬编码固定语言；中英文金额、日期、时区口径一致 |

## 5. 全局业务概念与不变量

### 5.1 组织模型

- `实例`代表一次私有部署，只服务一个客户集团。
- `组织`代表独立经营和核算的法人实体，拥有本位币、时区、科目、期间、仓库、编号和业务数据。
- `部门`用于组织内岗位归属、数据范围和审批人解析，不承担法人核算。
- 一个用户身份可拥有多个组织成员关系；每个成员关系拥有独立部门、角色和状态。
- 每个会话必须有且只有一个当前组织。跨组织汇总为只读查询，不能借汇总上下文执行写操作。
- 2.0 的客户、供应商、商品、价格、仓库和科目默认组织专属，不建设集团共享主数据及同步治理。

### 5.2 单据与来源

- 每张正式单据包含组织、编号、业务日期、币种、汇率、交易方、负责人、版本和审计字段。
- 每一行后续单据都保存来源类型、来源单据 ID、来源行 ID 和本次处理数量/金额。
- 已被后续单据引用的来源行不能硬删除；允许关闭剩余量，但必须记录原因、操作者和时间。
- 草稿可编辑；进入审批后核心字段锁定。退回修改会创建新修订并重新执行适用流程。
- 已确认、已过账或已结算单据不能直接编辑金额、数量、币种、组织或来源关系。
- 业务数据默认逻辑归档；存在引用或过账结果的数据不允许物理删除。

### 5.3 数量、金额与时间

- 数量、单价、金额、汇率和税率使用定点数，不使用二进制浮点数。
- 单据保存交易币金额、记账时汇率和本位币金额；历史单据不因汇率主数据变化而重算。
- 行金额先按币种精度舍入，税额按组织配置的行级或单据级口径计算；同一组织内口径必须一致。
- 服务端时间戳以 UTC 存储和传输，业务日期按当前组织时区解释。
- `businessDate` 表示业务实际发生日，`accountingDate` 决定总账和财务期间，`exchangeRateDate` 决定过账汇率，`postedAt` 表示系统实际完成过账的 UTC 时间戳；这些字段不得混用。
- 正常情况下 `accountingDate` 和 `exchangeRateDate` 等于 `businessDate`。业务日期位于关闭期间时，保留原业务日期，将会计日期设为组织时区下最早可用开放期间日期，并默认以该会计日期作为汇率日期。
- 财务、税额管理报表按会计日期归期；销售/采购/库存运营报表按业务日期；账龄按合同到期日。任何报表都应标明采用的日期口径。
- 发票到期日默认按发票 `businessDate + paymentTerms` 计算，也可由有权限用户在过账前明确调整；关账导致会计日期顺延时不自动顺延合同到期日。
- 编号在“组织 + 单据类型 + 财年/编号规则”范围内唯一，已使用编号不回收。

### 5.4 并发与幂等

- 所有实体更新携带版本号；过期版本返回稳定的并发冲突错误。
- 提交、审批、过账、收发货、收付款、退款、冲销和导入等关键写操作要求幂等键。
- 同一来源事件只能生成一次库存流水、财务凭证或异步事件。
- 库存扣减和预留使用数据库锁或等价原子机制，正常业务不能把实物在手扣为负数，也不能在净可承诺量不足时接受新预留。

## 6. 核心业务流程

### 6.1 登录与组织切换

```text
登录 → 完成强制改密/MFA（如适用） → 选择授权组织 → 加载成员角色与数据范围 → 进入工作台
```

- 只有一个可用组织时自动进入；多个组织时使用上次组织或要求选择。
- 切换组织必须验证成员关系并重建服务端安全上下文，不能仅修改前端参数。
- 当前页面在新组织中不可访问时，切换后回到工作台并提示原因。
- 切换、失败切换和管理员代为重置会话都写入安全审计。

### 6.2 订单到收款与退货退款

```text
报价 → 审批 → 销售订单 → 信用检查 → 库存预留 → 出库/服务履约
     → 销售发票 → 收款与核销 → 完成

原出库 → 销售退货入库 ┐
原发票 → 销售贷项 ────┼→ 退款或冲抵后续应收
```

- 报价和订单支持多行商品/服务、行级折扣、税率、仓库、项目和期望日期。
- 订单确认前执行客户状态、信用额度、价格权限和库存策略校验；超限按组织配置阻止或进入审批。
- 库存商品按订单行预留；服务行不占库存，可按里程碑、工时费用或手工确认形成开票依据。
- 销售发票可以引用一个或多个交付/服务依据，但累计开票数量和金额不得超过可开票余额。
- 销售退货必须引用原出库行，退货数量不得超过原出库净数量；使用原出库成本反向入库。
- 销售贷项必须引用原发票行，累计贷项不得超过原发票净额；贷项与实物退货可以关联但不强制同日完成。
- 退款必须基于可退款余额，可退款余额不得被重复退款或重复核销。

### 6.3 采购到付款与采购退货

```text
采购申请 → 审批 → 采购订单 → 审批 → 收货/上架 → 供应商发票
         → 三单匹配 → 付款与核销 → 完成

原收货 → 采购退货出库 ┐
原发票 → 供应商贷项 ──┼→ 供应商退款或冲抵后续应付
```

- 采购申请可不指定供应商；采购订单必须指定供应商、币种、条款和组织内收货仓库。
- 收货支持分批、库位、批次/序列号和保质期；超收默认禁止，容差必须显式配置并受权限控制。
- 供应商发票支持引用多个采购订单和收货行。
- 三单匹配比较订单、收货和发票的数量、单价与税额；超出容差进入异常队列并阻止过账。
- 采购退货必须引用原收货行；累计退货不能超过净收货量，已被下游消耗或预留的库存不能直接退货。
- 供应商贷项和退款遵循与销售侧对称的来源、余额与核销规则。

### 6.4 库存预留与追溯

```text
订单需求 → 仓库级预留 → 库位/批次/序列号分配 → 拣货确认 → 出库过账 → 追溯报告
```

- 可用数量 = 在手数量 − 有效预留数量 − 冻结数量 − 不可售过期数量。
- 预留最初绑定组织、仓库、商品和来源订单行；拣货时再绑定具体库位、批次或序列号。
- 默认按先到期先出提供建议，但 2.0 的存货计价仍为移动加权平均，不采用 FIFO 成本法。
- 序列号在同一组织内唯一，每个有效序列号的在手数量只能为 0 或 1。
- 过期或冻结库存不能通过正常出库使用，只能解冻、调整、报废或按受控流程退回。
- 追溯报告必须覆盖供应商/收货、内部移动、当前库位、销售出库、客户和退货记录。

### 6.5 项目交付与开票

```text
客户/销售订单 → 项目 → 里程碑/任务 → 工时与费用审批
              → 可计费依据 → 草稿销售发票 → 财务审核过账
```

- 项目支持固定价、里程碑和工时费用三种计费模式，一个项目只能选择一种主计费模式。
- 工时记录必须包含人员、任务、日期、小时、成本率、计费率和是否可计费。
- 费用必须保存费用类别、金额、币种、凭证附件和是否可计费；没有附件的例外由组织规则决定。
- 已批准且未开票的工时、费用或里程碑可汇总生成草稿销售发票，不能直接生成已过账发票。
- 发票过账后回写已开票数量/金额；贷项后相应释放可再次开票额度或标记为取消计费。
- 项目可以查看销售、工时、费用、采购、库存消耗和分摊来源；实际财务收入/成本以对应已过账总账行去重汇总，未过账工时成本与采购承诺单独展示。

### 6.6 月末结账

```text
检查未过账业务 → 银行与往来对账 → 库存/总账核对 → 外币重估
              → 生成报表 → 期间关闭 → 受控重开/更正
```

- 关闭前必须运行可配置检查清单，至少检查未过账库存、未平三单、未完成银行对账和借贷不平衡。
- 期间关闭后禁止新增或修改该期间的业务过账；迟到业务保留原 `businessDate`，使用最早开放期间的 `accountingDate` 和默认同日 `exchangeRateDate`，提交前向用户明确展示两套日期。
- 重开期间需要独立权限、原因和可选审批；重开、补记和再次关闭均写入审计。
- 重估凭证保存汇率来源和计算明细，下期可按组织策略自动反转。

### 6.7 配置式审批

```text
草稿提交 → 解析已发布模板版本 → 创建流程实例 → 串行/并行任务
         → 批准 / 退回修改 / 驳回 / 转交 / 委托 → 完成或终止
```

- 按组织、资源类型、生效时间和条件筛选已发布模板，再选择最高优先级；同一最高优先级命中多个模板时阻止提交并告警。无匹配模板时使用组织明确配置的自动通过或禁止提交策略。
- 条件只允许使用白名单字段、比较运算符和逻辑组合，不允许执行脚本、SQL 或任意表达式。
- 审批人可由固定用户、角色、部门负责人、单据负责人或金额层级解析。
- 并行步骤支持“全部通过”和“任一通过”；2.0 不实现自定义票数或复杂仲裁算法。
- 默认禁止申请人审批本人发起的单据；组织可为低风险场景显式放开，并保留审计。
- 模板发布后不可编辑；变更通过复制草稿并发布新版本完成，运行实例继续使用原版本。

## 8. 状态模型

### 8.1 状态设计原则

2.0 不使用一个枚举同时表达审批、履约、开票和结算。页面可以显示聚合标签，但数据库和 API 必须保留独立状态维度，并由明细数量或金额推导聚合结果。

### 8.2 通用生命周期与审批状态

| 维度 | 状态 | 规则 |
| --- | --- | --- |
| 生命周期 | `DRAFT` | 尚未形成正式业务承诺或过账事实；能否编辑由当前修订的审批状态决定 |
| 生命周期 | `CONFIRMED` / `POSTED` | 已确认业务承诺或已产生账务/库存结果 |
| 生命周期 | `CLOSED` | 剩余量经正常完成或受控关闭，不再接受新执行 |
| 生命周期 | `CANCELLED` | 仅未过账且无下游结果的单据可取消 |
| 审批 | `NOT_SUBMITTED` | 当前修订尚未提交审批 |
| 审批 | `NOT_REQUIRED` | 组织策略明确自动通过，仍记录决策依据 |
| 审批 | `PENDING` | 存在运行中流程实例 |
| 审批 | `APPROVED` | 当前修订已获批准 |
| 审批 | `RETURNED` | 当前修订被退回并终止；修改发生在关联的新草稿修订 |
| 审批 | `REJECTED` | 当前修订终止，不能直接转为已批准 |
| 审批 | `WITHDRAWN` | 当前修订由发起人撤回并终止；如继续办理则创建新草稿修订 |

典型迁移为 `DRAFT + NOT_SUBMITTED → DRAFT + PENDING → DRAFT + APPROVED → CONFIRMED/POSTED + APPROVED`。自动通过时使用 `DRAFT + NOT_REQUIRED → CONFIRMED/POSTED + NOT_REQUIRED`。处于 `PENDING` 的修订锁定核心字段；只有 `DRAFT + NOT_SUBMITTED` 且无引用的修订可以删除。

### 8.3 销售与采购单据状态维度

| 单据 | 独立状态维度 |
| --- | --- |
| 报价 | 生命周期；审批；转换 `NOT_CONVERTED / PARTIAL / CONVERTED`；有效性由有效期推导 |
| 销售订单 | 生命周期；审批；预留 `NONE / PARTIAL / FULL`；履约 `NOT_STARTED / PARTIAL / COMPLETE`；退货 `NONE / PARTIAL / FULL`；开票 `UNBILLED / PARTIAL / BILLED` |
| 采购申请 | 生命周期；审批；转单 `NOT_CONVERTED / PARTIAL / CONVERTED` |
| 采购订单 | 生命周期；审批；收货 `NOT_STARTED / PARTIAL / COMPLETE`；退货 `NONE / PARTIAL / FULL`；开票 `UNBILLED / PARTIAL / BILLED` |
| 销售/采购退货 | 生命周期 `DRAFT → POSTED`，审批独立；获批后才能过账。未过账可取消，已过账错误通过反向单据处理 |

- 部分状态按所有行的净数量推导，不能由客户端直接设置。
- `CLOSED` 可以在剩余量为零时自动产生，也可以由有权限用户关闭剩余量；手工关闭必须填写原因。
- 已完全履约或收货不等于已开票，已开票不等于已收付款。

### 8.4 库存状态

| 对象 | 状态及规则 |
| --- | --- |
| 库存操作单 | 生命周期 `DRAFT → POSTED`，审批独立；未过账可 `CANCELLED`；反向结果另为 `NONE / PARTIAL / FULL` |
| 预留 | 消耗状态 `ACTIVE → PARTIALLY_CONSUMED → CONSUMED`，或进入 `RELEASED / EXPIRED` 终态；分配状态另为 `UNALLOCATED / PARTIAL / FULL / NEEDS_REALLOCATION` |
| 批次 | 管理状态 `ACTIVE / BLOCKED / CLOSED`；过期为根据失效日期推导的独立属性 |
| 序列号 | `AVAILABLE / RESERVED / ISSUED / RETURNED / BLOCKED / SCRAPPED`，每次变化必须有库存流水 |
| 库位 | `ACTIVE / INACTIVE`；停用前在手、预留和在途数量必须为零 |

### 8.5 发票、付款和凭证状态

| 对象 | 生命周期 | 独立结果状态 |
| --- | --- | --- |
| 销售/供应商发票 | `DRAFT → POSTED`，审批独立；草稿可取消 | 结算 `UNPAID / PARTIAL / PAID`；贷项 `NONE / PARTIAL / FULL` |
| 销售/供应商贷项 | `DRAFT → POSTED`，审批独立 | 核销 `UNAPPLIED / PARTIAL / APPLIED`；退款 `NONE / PARTIAL / FULL` |
| 收款/付款/退款 | `DRAFT → POSTED`，审批独立 | 分配 `UNALLOCATED / PARTIAL / ALLOCATED`；错误通过反向付款处理 |
| 手工凭证 | `DRAFT → POSTED`，审批独立 | 冲销结果 `NONE / FULL`；原分录保持不变 |
| 会计期间 | `OPEN / CLOSED` | 重开是受审计动作，重开后状态重新为 `OPEN` |

### 8.6 工作流状态

| 对象 | 状态 |
| --- | --- |
| 模板 | `DRAFT → PUBLISHED → RETIRED` |
| 流程实例 | `RUNNING → APPROVED / REJECTED / RETURNED / WITHDRAWN / TERMINATED` |
| 审批步骤 | `WAITING → ACTIVE → COMPLETED / SKIPPED / CANCELLED` |
| 审批任务 | `OPEN → APPROVED / REJECTED / RETURNED / TRANSFERRED / CANCELLED` |

`TRANSFERRED` 的原任务终止，同时为新处理人创建关联任务；历史任务不会被覆盖。

### 8.7 项目状态

| 对象 | 状态与迁移 |
| --- | --- |
| 项目 | `PLANNED → ACTIVE ↔ AT_RISK ↔ ON_HOLD → COMPLETED → ARCHIVED`；非终态可受控归档 |
| 里程碑 | `PLANNED → IN_PROGRESS → COMPLETED`，或在未开票时 `CANCELLED` |
| 任务 | `TODO → IN_PROGRESS ↔ BLOCKED → DONE`；未发生工时前可取消 |
| 工时 | 生命周期 `DRAFT → CONFIRMED`，审批使用通用独立状态；计费另为 `UNBILLED / PARTIAL / BILLED`，退回/撤回创建新修订 |
| 费用 | 生命周期 `DRAFT → CONFIRMED`，审批使用通用独立状态；计费和报销结果分别维护，退回/撤回创建新修订 |

## 9. 权限模型与默认角色矩阵

### 9.1 权限判断顺序

每次业务访问依次检查：

1. 用户、会话、组织成员关系是否有效。
2. 当前组织是否允许该业务动作。
3. 用户是否拥有资源动作权限。
4. 目标数据是否落在用户数据范围内。
5. 是否满足职责分离、本人审批、金额权限和业务状态限制。
6. 是否需要工作流批准或二次确认。

任何一步失败都返回稳定错误码并记录必要的安全信息；错误响应不泄露其他组织资源是否存在。

### 9.3 敏感动作

以下动作始终单独授权，不能仅因拥有模块管理权限而自动获得：

- 修改角色权限、重置管理员密码、关闭或重开会计期间。
- 导出用户、财务、银行、审计和跨组织数据。
- 批准本人单据、超信用下单、超容差收货或三单匹配例外。
- 冻结/解冻库存、过期库存处置、库存调整和反向库存流水。
- 过账、冲销、退款、解除核销、删除暂存附件和重发死信事件。

## 10. 库存、金额与财务规则

### 10.1 库存数量口径

```text
在手数量 = 所有已过账入库数量 − 所有已过账出库数量
合格在手 = 位于有效库位且未冻结、未过期、未报废的在手数量
有效预留 = 已生效且未释放、未过期、未完全消耗的预留余额
净可承诺量 = 合格在手 − 有效预留
可用于新预留 = max(0, 净可承诺量)
预留短缺 = max(0, 有效预留 − 合格在手)
```

- 在手数量可以包含冻结和过期库存，但冻结/过期已在“合格在手”中排除，计算时不得再次重复扣减。
- 禁止任何正常出库、调拨出库、采购退货或负向调整使实物在手低于零；禁止新预留使当时净可承诺量低于零。
- 质量冻结、失效日期到达或库位停用可能使既有预留产生短缺；系统保留业务承诺、将相关分配标记为 `NEEDS_REALLOCATION`、阻止出库并生成缺货告警，不静默释放订单预留。
- 重新分配成功后恢复 `PARTIAL/FULL`；只有订单取消、关闭剩余量、预留到期或有权限用户显式释放才减少有效预留。
- 预留不能改变在手数量；出库消耗预留时，在同一事务内减少在手并结转预留。
- 库存汇总由不可变流水重建后必须与余额表一致；余额表是性能投影，不是审计真相的唯一来源。

### 10.2 移动加权平均成本

普通采购入库或正向调整后：

```text
新平均成本 = (原在手数量 × 原平均成本 + 本次入库数量 × 本次单位成本) / 新在手数量
```

- 销售出库按出库时的当前平均成本结转销售成本，出库不改变剩余平均成本。
- 同仓库库位移动不改变成本；跨仓调拨按源仓实际成本转出，并以相同成本进入目标仓平均成本计算。
- 销售退货按原销售出库成本恢复库存；采购退货按原采购收货成本减少库存。
- 批次和序列号记录来源成本用于追溯，但 2.0 不按批次或序列号独立计价。
- 退货、反向和调拨造成的舍入差额进入组织配置的库存差异科目，不允许静默丢弃。

### 10.3 税、汇率与舍入

- 组织定义金额小数位、单价小数位、数量小数位和税额舍入方式；已确认单据保存当时规则快照。
- 单据行可以选择一个税规则，税规则由一个或多个税组成项构成；各组成项分别计算并过账。
- 单据必须保存交易币、本位币、汇率日期和使用汇率。非本位币汇率必须大于零。
- 会计日期决定凭证所属期间；汇率日期默认等于会计日期。具有汇率覆盖权限的用户可以使用其他有效汇率日期或手工汇率，但必须填写原因并审计。
- 客户/供应商发票过账时确认本位币往来；结算时按结算日汇率计算已实现汇兑差额。
- 报表汇总中的舍入差异必须显示为明确调整行，不能修改历史明细以强行对平。

### 10.4 自动记账映射

实际科目由组织的业务科目映射决定。下表固定业务语义，配置只能替换科目，不能改变借贷方向。

| 业务动作 | 借方 | 贷方 |
| --- | --- | --- |
| 采购收货 | 库存资产 | 应付暂估 |
| 供应商发票—已收货商品 | 应付暂估、可抵扣税额、价格差异（如有） | 应付账款 |
| 供应商发票—服务/费用 | 费用或项目成本、可抵扣税额 | 应付账款 |
| 采购退货 | 应付暂估 | 库存资产 |
| 供应商贷项 | 应付账款 | 应付暂估/费用、可抵扣税额 |
| 供应商付款 | 应付账款 | 银行/现金 |
| 供应商退款 | 银行/现金 | 应付账款或供应商贷方余额 |
| 销售出库 | 销售成本 | 库存资产 |
| 销售退货 | 库存资产 | 销售成本 |
| 销售发票 | 应收账款 | 销售收入、应交税费 |
| 销售贷项 | 销售收入、应交税费 | 应收账款 |
| 客户收款 | 银行/现金 | 应收账款 |
| 客户退款 | 应收账款或客户贷方余额 | 银行/现金 |
| 库存盘盈 | 库存资产 | 库存差异收益 |
| 库存盘亏/报废 | 库存差异损失 | 库存资产 |
| 外币重估损失 | 未实现汇兑损失 | 外币往来/银行调整 |
| 外币重估收益 | 外币往来/银行调整 | 未实现汇兑收益 |

- 采购退货与供应商贷项、销售退货与销售贷项是不同业务事件，可以分时发生，但必须能够互相核对。
- 同一组织、来源事件类型和来源 ID 只能生成一组自动凭证。
- 自动凭证保存规则版本、来源单据和来源行汇总；科目映射缺失时禁止业务过账并返回可定位错误。

### 10.5 三单匹配

对每个供应商发票行计算：

```text
数量差异 = 发票数量 − 可开票收货数量
价格差异率 = abs(发票未税单价 − 订单未税单价) / 订单未税单价
税额差异 = 发票税额 − 按组织税规则计算的期望税额
```

- 差异在组织容差内时可以正常过账并记录差异。
- 超容差时进入 `MATCH_EXCEPTION`，只有具备例外批准权限且满足工作流后才能过账。
- 同一收货行的累计已开票数量扣除贷项后不能超过允许数量。

### 10.6 预算控制

- 预算可以按组织、年度/月度、科目、部门和项目组合建立。
- 预算执行至少展示预算、已过账实际、已承诺采购和可用余额。
- 组织可为不同预算维度配置仅提示、阻止或审批三种超预算策略。
- 预算控制不修改总账事实；预算调整产生版本和审计记录。

## 11. 领域模型

所有业务实体必须包含 `organization_id`、创建/更新时间、创建/更新用户和乐观锁版本；可过账实体还包含业务日期、会计日期、汇率日期和实际过账时间，不可变流水另包含来源引用和请求 ID。

父子表和跨资源引用必须保证组织一致；优先使用组织参与的唯一键/外键约束，并在服务事务中做二次校验，不能只依赖前端传值。

### 11.1 实例、身份与组织

- `instance_setting`：实例标识、安全、邮件、存储和运维配置的非秘密部分。
- `user_identity`：用户名、显示名、密码摘要、状态、失败次数、锁定与最后登录时间。
- `user_mfa` / `password_reset_token`：MFA 密钥加密信息、恢复码摘要和一次性重置令牌。
- `organization`：名称、状态、本位币、时区、财年和业务口径。
- `department`：组织内树结构、负责人和状态。
- `organization_membership`：用户、组织、部门、默认组织标记和成员状态。
- `role` / `permission` / `role_permission` / `membership_role`：组织角色、资源动作权限和成员授权。
- `session`：Redis 会话；数据库只保留必要的安全审计，不复制可重用会话凭据。
- `security_event` / `audit_event`：安全事件和业务变更事件，采用只追加模型。

### 11.2 工作流与协作

- `workflow_template` / `workflow_version`：模板身份、版本、生效条件和发布状态。

- `workflow_instance` / `workflow_step_instance` / `workflow_task`：运行快照、步骤状态、实际处理人与决策。

- `comment` / `mention` / `activity_event`：评论、提及与系统活动。
- `attachment`：资源引用、对象键、校验和、大小、类型和状态。

## 12. API 与工程契约

### 12.1 版本策略

- `/api/v2` 是 2.0 前端和新能力的标准契约。
- 2.0 前端在切换生产写入前必须全部迁移到 v2；不得混用 v1 业务写接口。
- `/api/v1` 在 2.0 和 2.1 仅保留认证/会话及可无损表达的只读查询；所有业务状态变更返回 HTTP 426 和 `API_VERSION_READ_ONLY`。
- v2 多行或追踪资源无法无损映射到 v1 时返回 `API_VERSION_UPGRADE_REQUIRED`，禁止只返回第一行或伪造旧语义。
- v1 兼容层只修复安全和查询缺陷，不增加 2.0 新能力。
- v1 移除时间必须至少提前一个小版本在发布说明和响应弃用信息中公告。

### 12.2 通用响应

成功响应继续使用：

```json
{
  "data": {},
  "requestId": "..."
}
```

失败响应继续使用：

```json
{
  "code": "STABLE_ERROR_CODE",
  "messageKey": "error.message.key",
  "args": {},
  "fieldErrors": [],
  "requestId": "..."
}
```

- API 不返回固定中文业务文案。
- 时间为 ISO 8601，时间戳带 UTC 偏移；日期不隐式转换时区。
- API 分别暴露 `businessDate`、`accountingDate`、`exchangeRateDate`、`dueDate` 和 `postedAt`；客户端不得用一个通用 `date` 字段猜测财务期间。
- 金额和高精度数量在 JSON 中使用十进制字符串或经 OpenAPI 明确约束的十进制格式。
- 枚举值使用稳定英文大写代码，显示名称由前端国际化。


OpenAPI 负责字段、格式、示例和 HTTP 状态；本 PRD 负责业务语义、状态、权限和验收。二者冲突时必须先修正文档并评审，不能由实现自行选择。

### 12.4 会话、组织与安全

- 继续使用服务端会话和 CSRF 防护；Cookie 默认 `HttpOnly`、`Secure` 和适当的 `SameSite`。
- 组织切换使用专用动作，成功后轮换会话标识并返回当前成员、角色和有效权限摘要。
- 服务端不能依据客户端提交的角色、权限、本位币或组织名称做授权决定。
- CORS 使用精确允许列表；生产不允许通配来源与凭据组合。

### 12.5 查询、分页与导出

- 列表使用服务端分页、稳定排序和白名单筛选；默认页大小 20，最大页大小由资源定义且不超过 200。
- 查询必须在权限过滤后计算总数和聚合，防止通过计数推断越权数据。
- 大型导出返回后台任务 ID，任务查询和结果下载继续执行资源权限检查。
- 下载链接短时有效、一次会话可控，不把对象存储永久地址暴露给客户端。

### 12.6 写操作、并发与幂等

- 所有更新请求携带 `version` 或 `If-Match`；冲突返回 `OPTIMISTIC_LOCK_CONFLICT` 和最新版本摘要。
- 财务、库存、流程动作和导入等关键写操作携带 `Idempotency-Key`。
- 幂等记录绑定当前组织、用户、操作和请求摘要；相同键不同请求返回冲突，不能复用旧结果执行新操作。
- 状态迁移使用动作端点而不是通用字段更新，例如提交、批准、过账、冲销、关闭和重开。

### 12.7 稳定错误类别

至少提供以下错误类别：

- `AUTHENTICATION_REQUIRED`、`INVALID_CREDENTIALS`、`ACCOUNT_LOCKED`、`MFA_REQUIRED`。
- `PERMISSION_DENIED`、`ORGANIZATION_ACCESS_DENIED`、`DATA_SCOPE_DENIED`、`SEGREGATION_OF_DUTIES_VIOLATION`。
- `RESOURCE_NOT_FOUND`、`VALIDATION_FAILED`、`DUPLICATE_CODE`、`REFERENCE_CONFLICT`。
- `WORKFLOW_NOT_CONFIGURED`、`WORKFLOW_STATE_CONFLICT`、`APPROVER_RESOLUTION_FAILED`。
- `INSUFFICIENT_AVAILABLE_STOCK`、`TRACKING_REQUIRED`、`LOT_EXPIRED`、`SERIAL_STATE_CONFLICT`。
- `MATCH_TOLERANCE_EXCEEDED`、`PERIOD_CLOSED`、`JOURNAL_UNBALANCED`、`ACCOUNT_MAPPING_MISSING`。
- `IDEMPOTENCY_CONFLICT`、`OPTIMISTIC_LOCK_CONFLICT`、`ASYNC_JOB_FAILED`。
- `API_VERSION_READ_ONLY`、`API_VERSION_UPGRADE_REQUIRED`。

### 12.8 内部事件

- 业务事务在同一数据库事务内写入 Outbox，提交后由内部工作进程投递。
- 事件至少包含事件 ID、组织、类型、资源、发生时间、模式版本和最少必要载荷。
- 2.0 的内部事件只服务站内通知、邮件、审计和投影刷新，不作为对外 Webhook 契约。

## 13. 信息架构、交互与国际化

### 13.1 导航结构

一级导航保持：工作台、流程、销售、采购、库存、财务、项目、分析和系统设置。二级导航按资源列表、待处理工作和报表组织，避免在一个巨型页面中堆叠全部功能。

### 13.2 单据体验

- 所有单据采用“头信息 + 多行明细 + 金额汇总 + 流程 + 活动时间线”的一致结构。
- 详情页同时展示生命周期、审批、履约/收货、开票和结算状态，不用单一颜色标签隐藏差异。
- 来源与后续单据以可点击关系链展示，用户可以从任一结果返回原单和原行。
- 危险动作使用明确动词、结果预览和二次确认，不使用含糊的“确定”。
- 表单保存草稿时可局部提示，提交/过账必须服务端完整校验并聚合返回字段错误。

### 13.3 响应式范围

- 1280 px 及以上提供完整配置、表格、报表和批量操作。
- 768–1279 px 支持所有核心业务，但复杂表格可切换卡片或横向滚动。
- 375–767 px 重点支持工作台、审批、通知、搜索、扫码、盘点、拣货确认和轻量表单。
- 流程设计器、权限矩阵、复杂财务报表在手机端只读或提示使用桌面端，不宣称完整移动编辑。

### 13.4 可访问性

- P0 表单、登录、导航、审批和业务动作支持键盘操作、可见焦点、标签关联和错误朗读。
- 颜色不作为唯一状态表达；文本与关键控件达到 WCAG 2.1 AA 的对比度目标。
- 表格、弹窗和异步加载提供可识别标题、空状态、加载状态和失败重试入口。

### 13.5 国际化

- 中英文资源必须在同一变更中交付，禁止以硬编码中文完成 P0/P1 页面。
- API 错误、流程动作、状态、权限和审计动作使用稳定代码，通过语言包显示。
- 日期按组织时区和用户语言显示；财务业务日期不因用户个人时区改变。
- 金额同时标明币种；跨币种汇总必须显示报告币种和汇率日期。
- 用户输入的名称、评论和附件文件名不自动翻译。

## 14. 非功能需求

### 14.1 安全

- 所有业务接口默认拒绝访问；无法解析合法认证主体或当前组织时必须失败关闭，禁止回退到 `org-demo` 或任意默认用户。
- 密码只保存自适应单向摘要；现有 BCrypt 摘要可兼容验证并在成功登录时按新参数重算，不保存或记录明文。
- 密钥、数据库密码、Redis 密码、SMTP 凭据、对象存储凭据和 MFA 密钥不得进入仓库、日志或诊断包。
- 状态变更请求执行 CSRF 防护、输入校验、权限校验、状态校验和组织边界校验。
- 防范 SQL/JPQL 注入、XSS、越权、任意文件上传、路径穿越、会话固定和不安全直接对象引用。
- 登录、权限拒绝、管理员操作、敏感导出、过账、冲销和配置变化产生结构化安全/审计事件。
- 审计事件采用只追加语义，普通管理员不能修改或删除；任何保留期清理都需要实例级策略和独立审计。
- 依赖漏洞、密钥泄漏和许可证检查进入 CI；高危漏洞在正式发布前必须修复或形成经批准的风险接受记录。

### 14.2 性能与容量基准

默认试用基准：

- 100 个并发登录用户。
- 10 万张业务单据、每张平均 5 行。
- 100 万条库存流水和 100 万条财务分录。
- 10 万条活动/审计事件和 5 万个附件元数据记录。

在约定基准环境和预热后：

- 工作台、常用列表、详情和全局搜索 P95 ≤ 800 ms。
- 普通草稿创建/更新 P95 ≤ 1.0 s；不含外部邮件的正常业务动作 P95 ≤ 1.5 s。
- 95% 的审批提交后 5 秒内在任务箱可见。
- 小型同步导出限于 10,000 行；更大结果进入后台任务。
- 单个 HTTP 请求不得同步生成超大报表、发送邮件或扫描整个对象存储。

性能门禁必须使用生产等价 MySQL 和 Redis，不以 H2 或 Mock 结果替代。

### 14.3 可靠性与事务

- 单据、库存流水、财务凭证、审计事件和 Outbox 的强一致部分在同一数据库事务内提交。
- 邮件、通知、导出和分析投影采用最终一致；页面必须展示处理中、失败或最后刷新时间。
- 应用重启、消费者重复执行和网络超时不能生成重复库存、凭证、退款、审批决策或文件元数据。
- 业务事务不依赖 SMTP 在线；对象存储不可用时禁止完成需要附件作为必填依据的动作，并返回可重试错误。
- 任何自动重试都有最大次数、退避、死信和告警，不允许无限紧循环。

### 14.4 可观测性

- 所有服务输出 JSON 结构化日志，至少包含时间、级别、服务、环境、请求 ID、用户 ID、组织 ID、资源和错误码；敏感字段脱敏。
- 暴露 Prometheus 兼容指标：请求量/延迟/错误率、数据库池、Redis、会话、Outbox 积压/失败、后台任务、对象存储和 JVM。
- 提供 `livez` 和 `readyz`；就绪检查覆盖数据库、Redis 和必需存储，SMTP 状态单独展示而不阻止核心服务就绪。
- 关键错误可由请求 ID 关联 API 响应、日志、审计事件和异步投递。
- 默认告警至少覆盖高错误率、持续高延迟、数据库/Redis 不可用、磁盘不足、备份失败、死信增长和恢复演练逾期。

### 14.5 可维护性与兼容性

- 继续采用 Vue 3、TypeScript、Vite、Element Plus、Pinia、vue-i18n、Java 25、Spring Boot、MySQL、Redis 和 Flyway。
- 后端保持模块化单体，业务域之间通过明确服务接口和事件协作，禁止直接跨域修改对方表。
- 前端按路由和业务域拆包，2.0 正式构建不得出现主 bundle 超过约定 500 kB 警告而无风险说明。
- 支持当前主流 Chrome、Edge、Firefox 最近两个稳定版本；Safari 提供核心查询和审批兼容。
- 数据库迁移只能追加新版本，禁止修改已发布的 V1–V9 校验和。
- 所有 P0/P1 API、状态和错误码进入 OpenAPI 和变更日志。

### 14.6 隐私与数据治理

- 只收集 ERP 业务必要的联系人和用户信息；演示、测试和文档禁止使用真实个人或企业敏感数据。
- 用户停用不删除其历史审计身份；界面按权限最小化展示邮箱、电话、银行和财务信息。
- 备份、导出、诊断包和附件下载使用与在线业务一致或更严格的访问控制。
- 2.0 不承诺特定法规的数据保留期限；实例管理员依据企业政策配置保留与归档，财务和审计事实默认不自动删除。

## 15. 1.0 升级与兼容策略

### 15.1 升级原则

- 冻结 1.0 的 Flyway V1–V9，2.0 从 V10 开始前向迁移。
- 采用“扩展结构 → 回填数据 → 双读/适配验证 → v2 切换 → 2.1 清理旧结构”的方式。
- 2.0 升级过程不重新生成已有库存流水或会计凭证，不因模型升级改变历史业务日期和金额。
- 升级工具先检查后执行；任何阻断项都必须在写入前报告，不能边迁移边发现不可恢复冲突。
- 数据库迁移不承诺自动向下回滚；回退依赖升级前数据库、Redis 必要状态和附件的联合备份。

### 15.2 升级前检查

升级前至少检查：

- 当前应用版本、Flyway 校验和和数据库字符集符合支持矩阵。
- 所有 1.0 迁移已完成，不存在失败或手工改写的历史迁移。
- 组织、用户、角色、主数据和单据引用完整，无孤儿外键。
- 用户名转为实例级唯一后不存在重复；如重复则阻断并要求管理员先提供重命名映射。
- 库存余额与流水重算一致，所有仓库商品数量和价值控制数已保存。
- 应收、应付、收付款、凭证借贷和科目余额控制数已保存。
- 数据库和附件联合备份成功且完成可读性校验。
- 磁盘空间、停机窗口和升级账号权限满足要求。

### 15.3 数据映射

| 1.0 数据 | 2.0 处理 |
| --- | --- |
| `flowora_organization` | 保留 ID，成为第一个正式组织；`org-demo` 由管理员选择保留并重命名，或在确认无业务使用后归档，迁移不得自动删除 |
| `flowora_user_account` | 保留用户 ID，生成实例身份与该组织成员关系；占位密码账号标记 `RESET_REQUIRED`，不能使用占位摘要登录 |
| 1.0 角色 | 映射为组织角色模板并生成权限；无法识别的角色保留名称但不自动授予高权限 |
| 1.0 单组织关系 | 为现有用户、部门缺省值和业务数据补充正式成员/范围关系，不改变原组织 ID |
| 单行页面对应的头/行表 | 以现有行表为准迁移到 v2 多行结构；禁止把多行压缩成第一行 |
| 1.0 开放销售订单 | 因 1.0 在订单创建时已确认整单应收，为原订单生成不重复记账的 `MIGRATED_LEGACY` 销售发票影子并将开票维度视为已开票；剩余商品/服务可继续履约，后续履约只产生库存/成本，不再次生成收入或应收 |
| 1.0 历史销售出库 | 保留来源与原成本，可在 2.0 发起部分退货；相关销售贷项引用迁移发票影子，累计贷项和退款继续受净额限制 |
| 1.0 开放采购订单 | 历史收货对应的应付迁移为 `MIGRATED_LEGACY` 供应商发票影子；订单剩余量可继续收货，新收货按 2.0 先记应付暂估、再由正式供应商发票确认应付 |
| 1.0 历史采购收货 | 保留原成本并允许 2.0 采购退货；已形成历史应付的部分通过迁移供应商发票影子处理贷项，未发生的新收货不得沿用 1.0 直接应付语义 |
| 历史应收/应付依据 | 迁移为 `MIGRATED_LEGACY` 往来/发票影子单据，保存原来源和余额；单据内容只读但未结余额可被 2.0 收付款核销，不得再次生成迁移时的总账凭证 |
| 已结清历史往来 | 保留只读历史和核销结果，不为零余额重新创建可支付单据 |
| 库存余额与流水 | 每个仓库创建 `LEGACY-STOCK` 默认库位并承接现有数量；商品追踪方式默认为 `NONE` |
| 历史固定审批任务 | 绑定只读的 `LEGACY_FIXED_RULE` 流程快照；新提交使用新模板，历史实例不重新路由 |
| 历史凭证与分录 | 原样保留 ID、编号、金额、来源和状态；补充缺失维度时不得改变借贷控制数 |
| 演示控制与种子数据 | 仅在 demo profile 继续生效；生产配置禁用重置和自动种子 |

1.0 状态映射固定为：草稿映射 `DRAFT + NOT_SUBMITTED`；等待审批映射 `DRAFT + PENDING`；已批准/确认映射 `CONFIRMED + APPROVED/NOT_REQUIRED`；驳回映射 `DRAFT + REJECTED` 且原修订只读；取消映射 `CANCELLED`；部分履约/收货映射 `CONFIRMED` 加对应 `PARTIAL` 结果；完全履约/收货且无剩余动作时映射 `CLOSED` 加对应 `COMPLETE` 结果。迁移报告逐类统计状态映射数量。

### 15.4 管理员引导

- 因 1.0 没有可用的持久化生产密码，升级后使用一次性启动令牌创建或激活首个实例管理员。
- 启动令牌只能通过部署环境提供，不写入数据库明文或日志，成功使用后立即失效。
- 其他迁移用户由管理员发放临时密码或密码重置链接，并在首次登录强制改密。
- 升级向导要求确认组织名称、本位币、时区、财年、默认库位、角色映射和生产邮件/存储配置。

### 15.5 升级后核对

必须自动生成升级核对报告，至少比较：

- 组织、用户、角色、主数据、单据头和单据行数量。
- 每个仓库/商品的数量、平均成本和库存价值。
- 应收应付原值、已结算额和未结余额。
- 总账凭证数、分录数、借方合计、贷方合计和各科目余额。
- 审计事件主体、请求 ID 和来源引用完整率。
- 所有差异必须为零，或属于文档明确列出的展示性字段补充；金额和数量差异不允许豁免。

### 15.6 兼容与回退

- `/api/v1` 只为现有客户端提供认证/会话和可无损表达的读取；业务写请求统一拒绝，无法表达的 v2 资源要求升级客户端。
- 进入 v2 写入前必须部署已迁移到 v2 的 Web；不支持直接使用 1.0 应用继续写同一数据库。
- 正式切换前执行一次生产副本升级预演和完整业务冒烟测试。
- 切换失败时停止 2.0 写入，恢复联合备份并重新部署 1.0；不得用手工 SQL 局部删除已执行迁移。
- 2.1 清理旧列或兼容表前，必须确认 v1 兼容窗口结束并完成新的备份恢复演练。

## 16. 部署与运维需求

### 16.1 标准部署拓扑

2.0 提供 Linux + Docker Compose 的标准私有部署：

```text
Reverse Proxy / TLS
        │
Web SPA ─── Spring Boot API / Worker
                 │
       MySQL ─ Redis ─ Object Storage
                 │
              SMTP Relay
```

- Web、API、后台工作进程、MySQL、Redis 和对象存储均有固定兼容版本和健康检查。
- SMTP 可以暂时不可用，但生产环境必须明确配置邮件关闭或有效 SMTP，不能使用隐藏默认值。
- Kubernetes 和高可用部署只提供参考，不作为 2.0 支持基线。

### 16.2 配置与启动

- 提供独立 `production` 配置；缺少数据库、Redis、会话密钥、对象存储和允许来源等必需配置时启动失败。
- 生产默认开启安全 Cookie、TLS 终止要求、严格 CORS、数据库迁移校验并关闭 demo 功能。
- 秘密通过环境变量或只读挂载文件注入；配置示例只包含无效占位值。
- 数据库迁移使用独立受控步骤或带锁的单实例启动任务，禁止多个应用副本并发迁移。

### 16.3 备份与恢复

- 每日备份 MySQL 和附件对象，保存同一恢复点标识；仅备份数据库或附件都不算完整成功。
- 默认目标为 RPO 24 小时、RTO 4 小时，保留周期由实例管理员和企业政策配置。
- 备份加密、校验、失败告警，并至少每季度执行一次隔离环境恢复演练。
- 恢复后自动核对数据库版本、附件校验和、组织数、库存和财务控制数。
- Redis 会话和可重建缓存不要求灾难恢复；恢复后所有用户重新登录。

### 16.4 运维文档

必须提供：安装、配置、TLS、升级、回退、备份、恢复、监控、告警、日志定位、容量扩展、管理员重置和常见故障处理文档。

## 17. 测试与验收

### 17.1 当前质量基线与 2.0 补强

1.0 已有前端 lint、类型检查、Vitest、构建和后端 JUnit/package 门禁，但真实 MySQL/Redis 验证仍主要依赖人工；尚无完整浏览器端到端、真实依赖集成、API 破坏性变更、安全扫描、性能、迁移回放和备份恢复自动门禁。

2.0 必须建立分层质量体系，测试通过不以单一覆盖率或 Mock 数量代替真实业务验收。

### 17.2 拉取请求质量门禁

每个合并请求至少执行：

- 前端 lint、格式检查、TypeScript 类型检查、单元/组件测试和生产构建。
- 后端编译、静态检查、单元测试和 Spring 集成测试。
- Testcontainers 或等价方式启动受支持版本的 MySQL 和 Redis，验证真实事务、锁、约束、会话和 Flyway。
- OpenAPI 语法、前后端契约和相对目标分支的破坏性变更检查。
- Flyway 空库迁移、V1–V9 校验和检查和至少一个 1.0 小型快照升级。
- 关键 Playwright 端到端冒烟：登录/组织切换、销售、采购、审批和财务过账。
- 密钥泄漏、SAST 和依赖漏洞扫描。
- `git diff --check` 及文档链接、国际化键和迁移命名检查。

### 17.3 覆盖率最低门槛

- 本次变更代码总体覆盖率不低于 85%。
- 后端核心领域行覆盖率不低于 80%，分支覆盖率不低于 70%。
- 前端业务逻辑层行覆盖率不低于 75%，分支覆盖率不低于 65%。
- 权限、状态机、库存、财务、迁移和幂等属于强制测试域，不得用全局平均覆盖率掩盖空白。
- 覆盖率是最低门槛；缺失关键业务断言时，即使数字达标仍不得合并。

### 17.4 单元测试范围

- 所有状态机合法和非法迁移。
- 权限并集、数据范围、职责分离和本人审批限制。
- 多行金额、折扣、税组成项、币种舍入和汇率计算。
- 可用库存、预留消耗、FEFO 建议、批次/序列号约束和移动平均成本。
- 销售/采购净履约、退货上限、贷项上限和退款可用余额。
- 三单匹配容差、借贷平衡、期间限制、核销、冲销和汇兑。
- 工作流模板匹配、审批人解析、串并行完成规则、委托和超时。
- 项目计费依据、已开票回写、贷项释放和毛利口径。

### 17.5 集成与契约测试

- 数据库唯一键、组织一致性、外键、乐观锁和库存悲观锁。
- Redis 会话创建、轮换、过期、撤销和权限变更失效。
- 对象存储上传、校验、下载授权、暂存清理和缺失对象处理。
- Outbox 与业务事务原子性、重复消费、重试、死信和人工重发。
- SMTP 成功、临时失败、永久失败和敏感信息最小化。
- API v1 只读/升级拒绝行为、v2 多行契约、错误码、分页、权限过滤和幂等重放。

### 17.6 强制端到端场景

#### A. 多组织与权限

1. 同一用户加入组织 A 和 B，在 A 创建的客户、订单、附件、通知、缓存和导出结果不能在 B 获取。
2. 组织 A 和 B 可以使用相同业务编号，详情仍由组织边界唯一定位。
3. 切换组织后旧页面、旧请求和旧后台任务不能继续使用旧组织权限写入。
4. 列表、搜索、报表、附件、通知和导出全部执行 `ALL / DEPARTMENT / SELF / ASSIGNED` 矩阵。
5. 任意一条跨组织泄漏即判定发布失败。

#### B. 销售正向与反向闭环

```text
多行报价 → 审批 → 订单 → 部分预留 → 两次出库 → 两次开票 → 三次收款
→ 部分退货（可售/冻结处置）→ 部分贷项 → 退款与剩余应收核销
```

验收：订单净数量、预留、库存、成本、收入、税、应收、收款、贷项和退款全链一致，无重复结果。

#### C. 采购正向与反向闭环

```text
多行申请 → 审批 → 采购订单 → 分批收货 → 供应商发票三单匹配
→ 分次付款 → 部分采购退货 → 供应商贷项 → 退款/冲抵
```

验收：订单、收货、暂估、发票、应付、库存成本、付款和退货控制数一致；超容差未经批准不能过账。

#### D. 库存追溯与并发

- 从初始 100 件库存并发发起 200 次各 1 件出库，必须恰好 100 次成功、100 次库存冲突、期末数量为 0，且无重复流水或负库存。
- 同一订单并发预留不能超出可用量；同一序列号不能被两个任务同时预留或出库。
- 跨仓调拨任一侧失败时两侧均不落账；成功时数量和成本守恒。
- 任一批次/序列号可查到供应商、收货、库位、移动、客户、出库和退货全链。
- 过期、冻结和已报废库存不能进入普通预留或交付。

#### E. 财务正确性

- 每张已过账凭证借贷差额精确为零，同一幂等请求只产生一份凭证。
- 销售/采购子账、收付款、库存价值与总账控制账户无差异。
- 关闭期间禁止过账；重开、补记和重新关闭均有权限、审批和审计。
- 贷项和冲销不修改原凭证；原单、反向单和核销关系完整。
- 换算报表允许的展示舍入差异不超过报告币种最小单位，存储口径不得有未解释差异。

#### F. 工作流与协作

- 条件路由命中期望模板比例 100%，歧义模板不能发布。
- 模板发布新版本后，运行实例的步骤、审批人和结果不发生变化。
- 发起人、审批人、受托人和管理员的撤回、退回、驳回、转交与终止边界均验证。
- @提及不授予资源权限；失权用户不能从旧通知或附件链接访问资源。
- 邮件故障时核心业务成功、Outbox 可见；恢复后只发送一次有效通知。

#### G. 项目计费

- 固定价、里程碑和工时费用项目分别生成正确的草稿销售发票。
- 未批准或已开票工时/费用不能重复进入计费依据。
- 已计费、未计费和贷项释放金额之和与来源记录一致。
- 项目收入、人工、费用、采购和材料成本均可下钻，项目毛利计算无未解释差异。

#### H. 1.0 升级

- 使用空库、标准演示库、含部分履约/关闭期间/多币种的边界库和生产量级库分别升级。
- 校验行数、ID、状态、来源链、审计主体、库存数量/价值、往来余额、借贷和孤儿记录。
- 升级后继续完成一个 1.0 部分履约销售订单和一个部分收货采购订单，验证历史影子发票可核销、未来履约使用新语义且不重复确认收入、应收或应付。
- 验证 v1 业务写接口统一拒绝，v1 无损只读与 v2 多行资源升级提示符合契约。
- 生产量级基准数据的迁移和自动核对目标在 60 分钟内完成；实际停机窗口据预演结果确定。
- 未匹配业务数据必须为零；只有文档明确的展示字段补全可列入批准清单。

#### I. 部署与恢复

- 从全新环境按文档完成安装、管理员引导和两个组织初始化。
- 恢复数据库与附件联合备份，核对附件校验和、库存和财务控制数。
- 模拟 MySQL、Redis、对象存储、SMTP 和后台进程分别中断，验证健康、告警、降级和恢复行为。

### 17.7 性能与稳定性测试

- 使用固定版本、固定资源和固定数据生成器记录基准环境。
- 在 100 并发下持续 30 分钟，常用读 P95 ≤ 800 ms、普通写 P95 ≤ 1.5 s、看板 ≤ 2 s、HTTP 5xx < 0.1%。
- 同等环境下相对上一发布候选的关键接口性能退化不得超过 10%，否则必须解释并批准。
- 监测数据库慢查询、连接池、库存锁等待、Redis 延迟、Outbox 积压、GC 和内存稳定性。

### 17.8 UAT 与发布候选门禁

- 贸易批发和项目型服务各至少一个试点组织完成关键用户 UAT。
- 两类试点均完成一次完整业务月和月末结账。
- 全量回归 100% 通过，未关闭 P0/P1 缺陷为 0。
- 不存在未处置的 Critical/High 安全漏洞。
- 升级预演、性能测试、联合恢复演练和运维交接全部通过。

## 18. 分阶段实施计划

### 18.1 阶段与依赖

| 阶段 | 建议周期 | 主要交付 | 退出标准 |
| --- | ---: | --- | --- |
| M0：需求与技术契约 | 2–3 周 | 本 PRD、领域词汇、API v2 原则、权限目录、迁移设计、威胁模型和测试基线 | 产品、架构、财务、库存、测试共同评审通过；无未决 P0 语义 |
| M1：生产化平台 | 6–7 周 | 持久化认证、多组织、部门、RBAC、数据范围、会话治理和安全审计 | A/B 组织隔离矩阵通过；不再依赖内存账号或默认组织回退 |
| M2：流程与协作 | 6–7 周 | 版本化工作流、任务箱、委托、附件、@、邮件和 Outbox | 流程版本不可变；通知故障不丢业务；附件权限测试通过 |
| M3：贸易与进阶库存 | 8–10 周 | 多行销售/采购、预留、库位、批次/序列号、退货和基础拣货 | 正向/反向销售采购、并发库存和完整追溯通过 |

| M5：分析、升级与发布 | 6–8 周 | 分析中心、响应式优化、v1 只读兼容、1.0 升级、部署、监控、备份恢复和全量加固 | 试点、迁移、性能、恢复和 RC 门禁全部通过 |

总主体周期约 36–45 周，另预留 4–8 周试点反馈和风险缓冲。M3 可在 M2 接口稳定后并行部分领域工作，M4 必须基于 M3 已固定的业务事件和来源语义。

### 18.2 阶段交付规则

每个阶段必须：

1. 从评审通过的需求 ID 和技术设计开始。
2. 同步更新 OpenAPI、状态、权限、数据库迁移、国际化和运维影响。
3. 在合并前通过阶段相关自动化门禁。
4. 提供可部署的集成版本、演示数据和验收记录。
5. 记录已知限制、风险、指标变化和下一阶段依赖。

不得把所有模块分别开发到末期再首次集成库存、财务、工作流和权限。

### 18.3 团队与排期假设

上述周期按至少包含产品/业务分析、2 名后端、2 名前端、1 名测试以及兼职设计和运维能力估算。若长期少于 3 名全职工程人员，应延长周期，不削弱组织隔离、财务正确性、迁移或备份恢复门禁。

## 19. 发布与灰度策略

### 19.1 发布阶段

1. **Alpha**：内部环境完成自动化回归，并以生产等价配置持续运行至少 24 小时。
2. **Beta**：贸易和项目各一个试点组织启用 2.0 功能，至少运行 7 个工作日，记录权限、流程和异常反馈。
3. **RC**：两个试点完成完整业务月、月结、升级预演、性能和恢复演练；冻结破坏性变更。
4. **GA**：发布 2.0.0、升级指南、运维手册、已知限制和 v1 废弃计划。

### 19.2 功能开关

- 工作流新版、追踪库存、正式发票、项目计费和新版分析可按组织启用。
- 功能开关不能绕过数据库迁移、权限或财务一致性；关闭功能后仍可查看此前生成的历史结果。
- 试点组织启用前执行前置条件检查，例如商品追踪初始化、科目映射和流程模板发布。

### 19.3 No-Go 条件

出现任一情况不得继续扩大发布：

- 任意跨组织数据泄漏或权限绕过。
- 库存出现未解释负数、重复流水、批次/序列号重复占用或账实不符。
- 财务借贷不平、子账与总账差异、重复凭证或关闭期间绕过。
- 1.0 升级控制数差异、未批准的数据丢失或无法恢复。
- 未关闭 P0/P1 缺陷、Critical/High 安全漏洞或联合恢复演练失败。
- 关键业务成功率、错误率或延迟持续低于发布门槛。

### 19.4 上线后观察

上线 30 天内持续跟踪：

- 核心业务动作成功率目标 ≥ 99.5%。
- 跨组织泄漏、库存/财务对账差异和未审计关键动作均为 0。
- P0/P1 线上缺陷为 0；出现时立即停止扩大发布并评估回退。
- HTTP 5xx > 2% 持续 5 分钟或关键接口 P95 > 2 秒持续 10 分钟触发告警。
- 备份新鲜度、Outbox 死信、库存锁冲突、财务核对异常和磁盘容量在运维看板可见。

## 20. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 2.0 范围继续膨胀 | 延期且各模块浅尝辄止 | P2 边界冻结；MRP、门户、法定税务和连接器必须另立版本 |
| 1.0 财务语义直接套入正式发票 | 重复确认收入/应收应付 | 历史单据使用 `MIGRATED_LEGACY`，迁移不重复生成凭证 |
| 多组织只在查询层过滤 | 严重数据泄漏 | 当前组织服务端绑定、默认拒绝、父子组织约束和全表面 A/B 矩阵测试 |
| 细粒度权限难配置 | 管理员误配或系统不可用 | 默认岗位模板、权限预览、最后管理员保护和职责分离规则 |
| 批次/序列号导致库存复杂度激增 | 并发错误和性能退化 | 数量与成本维度分离、真实数据库并发测试、明确不做 FIFO 成本和完整 WMS |
| 工作流允许任意表达式 | 安全、性能和不可预测路由 | 白名单字段/运算符、发布校验、版本快照和无脚本策略 |
| 邮件/存储故障阻塞业务 | 可用性下降或附件丢失 | Outbox、对象暂存、重试/死信、健康告警和明确降级 |
| 生产化工作被功能开发挤压 | 无法真实试用 | M1 提前建设安全底座，M5 的迁移/恢复/性能为硬门禁 |
| 无真实用户数据 | 需求与流程可能偏离 | 两类试点贯穿 Beta/RC，记录任务数据并把新需求进入 2.x 而非临时扩展 |

## 21. 关键决策与默认假设

- 一个部署实例对应一个客户集团，不引入 SaaS 租户层。
- 组织代表独立核算法人；部门只用于组织内管理和数据范围。
- 主数据在 2.0 默认组织专属，不实现集团共享主数据治理。
- 用户一次只在一个活动组织中写业务，跨组织只读汇总不做内部抵销。
- 库存采用 FEFO 拣货建议，但成本继续使用移动加权平均，不引入 FIFO 成本法。
- 退货、库存处置、贷项和退款分别建模，不能用一个“退货”动作同时修改全部结果。
- 项目财务为管理口径的成本、计费和毛利，不实现会计准则级收入确认。
- `/api/v2` 承载全部新语义和业务写入，`/api/v1` 只在 2.0–2.1 提供认证及无损只读兼容。
- 数据库只做前向迁移；灾难回退使用升级前联合备份。
- 默认性能、RPO/RTO、密码和附件限制可以在安全范围内配置，但发布测试使用本文默认值。

## 22. 需求追踪与完成定义

每个 P0/P1 需求只有同时满足以下条件才算完成：

- 需求 ID 已关联设计、实现任务和验收用例。
- API、状态、权限、数据模型和错误码已在 OpenAPI/技术文档中定义且无冲突。
- 中文、英文、桌面和约定的响应式范围完成。
- 单元、集成、契约和适用的端到端测试通过。
- 组织隔离、数据范围、审计、幂等和并发影响已经验证。
- 涉及数据库时包含空库迁移、1.0 升级和控制数核对。
- 涉及异步、附件或运维时包含失败、重试、告警、备份和恢复路径。
- 发布说明、管理员/用户文档和已知限制同步更新。
- 产品、测试及相关业务负责人依据本文验收标准签收。

## 23. 术语表

| 术语 | 定义 |
| --- | --- |
| 实例 | 一次 Flowora 私有部署，对应一个客户集团，不是 SaaS 租户 |
| 组织 | 独立经营和核算的法人实体，拥有本位币、期间、科目和业务数据 |
| 当前组织 | 用户当前会话中唯一允许执行写操作的组织 |
| 数据范围 | 在资源动作权限之外，对可访问记录集合的限制，如全部、部门、本人或分配给我 |
| 源单 | 产生后续业务结果的上游单据或单据行 |
| 履约 | 商品交付或服务完成，不等同于开票和收款 |
| 过账 | 将库存或财务草稿确认为不可直接修改的正式事实 |
| 在手数量 | 已过账入库减已过账出库后的实物账面数量 |
| 可用数量 | 在手扣除有效预留、冻结和不可售过期数量后的可承诺数量 |
| 预留 | 为指定需求占用可用库存但尚未改变在手数量的记录 |
| 批次 | 一组共享批号和可选失效日期的同类商品 |
| 序列号 | 唯一标识一个实物单位并跟踪其生命周期的号码 |
| FEFO | First Expired, First Out；优先建议最早到期的可用库存 |
| 移动加权平均 | 每次计价入库后重算仓库商品平均成本的成本法 |
| 应付暂估 | 商品已收货但供应商发票尚未确认时使用的过渡负债 |
| 三单匹配 | 比较采购订单、采购收货和供应商发票的数量、价格与税额 |
| 贷项 | 对已过账销售/供应商发票进行部分或全部反向的正式单据 |
| 核销 | 将收付款或贷项分配到一个或多个往来单据的过程 |
| Outbox | 与业务事务同时写入、提交后异步投递的可靠事件记录 |
| `MIGRATED_LEGACY` | 由 1.0 历史应收应付迁移而来的来源标记；原单内容只读，未结余额仍可正常核销且不得重复生成迁移凭证 |
