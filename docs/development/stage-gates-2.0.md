# Flowora ERP 2.0 阶段目标与审核门禁

## 1. 执行规则

Flowora ERP 2.0 采用严格串行阶段交付：

1. 每个阶段从最新 `main` 创建独立的 `codex/2.0-m<编号>-<主题>` 分支；
2. 阶段范围冻结后，只实现该阶段工作，不提前混入下一阶段业务功能；
3. 完成代码、迁移、测试和文档后，运行该阶段的全部验证；
4. 推送 GitHub 并创建 Pull Request，附交付清单、测试证据、迁移影响和已知限制；
5. 用户审核通过后才合并或开始下一阶段；
6. 审核要求修改时，只在当前阶段分支修正并重新验证。

任何涉及数据丢失、权限降级、已记账数据修改或无法回滚的变更，均不得仅凭自动化测试放行。

## 2. M0：2.0 工程与契约基线

### 目标

在不改变 1.0 业务行为的前提下，建立 2.0 的版本、API、数据库迁移、质量和阶段治理基线。

### 交付物

- 2.0 PRD、开发实施规划及本阶段门禁；
- 2.0 架构演进 ADR；
- 项目版本切换为 `2.0.0-SNAPSHOT`；
- `/api/v2/system/version` 版本协商端点及 OpenAPI v2 基线；
- V1–V9 Flyway 迁移文件防篡改自动化测试；
- Maven Wrapper 3.9.16 与跨平台统一验证入口；
- 1.0 Web/API 回归验证和 M0 专项测试。

### 完成标准

- 1.0 现有业务测试全部通过；
- v1 现有端点行为不变；
- v2 版本端点返回产品版本、API 版本、兼容版本和当前阶段；
- V1–V9 任意内容或文件名被修改时，测试必须失败；
- 后续数据库迁移明确从 V10 开始；
- GitHub CI 全部通过。

## 3. M1：身份、组织、权限与主数据平台

### 目标

建立所有 2.0 业务域共同依赖的安全平台和多组织基础。

### 主要范围

- MFA、密码与会话安全；
- 多组织树、成员归属、组织切换和强制隔离；
- 角色、权限点、数据范围、权限缓存和敏感操作审计；
- 客户、供应商、商品、仓库、库位、币种、税率等主数据升级；
- API v2 通用错误、分页、过滤、幂等和并发约定；
- Web 应用壳、权限守卫与共享业务组件。

### 完成标准

- IAM、ORG、ACL、MST 的 P0 需求验收通过；
- 跨组织访问四象限测试通过；
- 所有授权由服务端执行，不依赖前端隐藏；
- M2–M4 可直接复用组织、权限、审计和主数据能力；
- V10+ 数据迁移可在空库和 1.0 样本库成功执行。

## 4. M2：流程与协作平台

### 目标

把 1.0 固定审批升级为可配置、可版本化、可委托、可追踪的通用工作流。

### 主要范围

- 审批模板、版本、节点、条件和适用范围；
- 审批实例、任务、同意、拒绝、退回、撤回和取消；
- 审批人解析、委托、SLA、催办和升级；
- 待办中心和单据内审批轨迹；
- 活动流、评论、提及、附件和通知；
- Outbox、重试、死信和手工重放。

### 完成标准

- 至少两个不同业务对象完成统一流程接入；
- 历史实例不受模板新版本影响；
- 重试和死信重放不产生重复副作用；
- 附件、评论和通知继承业务对象权限；
- WFL、COL 的 P0 需求验收通过。

## 5. M3：销售、采购与进阶库存

### 目标

建立支持部分履约、来源追踪、批次/序列号、库位与预留的贸易库存闭环。

### 主要范围

- 通用交易单据、金额税额和来源行框架；
- 报价、销售订单、预留、交付和销售退货；
- 采购申请、采购订单、收货和采购退货；
- 仓库、库位、批次、序列号、库存事件和余额；
- 预留、分配、调拨、盘点、冻结和质量处置；
- 财务来源事件，但不在本阶段伪造正式凭证。

### 完成标准

- SAL、PRC、INV 的 P0 主链和异常链通过；
- 并发测试无负库存、重复移动或超额履约；
- 任一库存变化可追到业务来源与操作者；
- 财务来源事件数量和金额可与交易单据核对。

## 6. M4：财务、银行与项目

### 目标

完成交易到发票、收付款、凭证、报表和项目盈利的财务闭环。

### 主要范围

- 客户/供应商发票、贷项、退款、收付款和核销；
- 自动凭证、会计期间、冲销和三单匹配；
- 银行流水导入、匹配与对账；
- 汇率、外币重估、预算和财务报表；
- 项目、里程碑、工时费用、计费和盈利分析。

### 完成标准

- FIN、PRJ 的 P0 需求验收通过；
- 试算平衡恒等，关键报表可穿透明细；
- 已记账数据只能通过冲销纠正；
- 月结、跨期、重估、银行对账和项目计费演练成功。

## 7. M5：分析、升级、加固与正式发布

### 目标

完成 1.0 到 2.0 的可重复升级、生产加固、试点和正式发布。

### 主要范围

- 角色工作台、全局搜索、分析、跨组织视图与导出；
- 管理诊断和演示数据；
- v1 认证/会话/无损读取兼容及业务写 HTTP 426；
- 1.0 预检、迁移、影子单据、控制总数和异常报告；
- Docker Compose、监控、告警、备份和恢复；
- 性能、安全、响应式、无障碍、Pilot、UAT 和 GA。

### 完成标准

- 所有 P0 和发布范围内 P1 验收通过；
- 至少两次全量迁移演练，控制总数相等或差异完成签字；
- 性能、安全、兼容和恢复门禁通过；
- Pilot 观察期无阻断缺陷；
- 产品、技术、QA、运维和业务共同批准 GA。

## 8. 每阶段 Pull Request 必备内容

- 本阶段目标和实际交付；
- 关联的 PRD ID 与工作包 ID；
- 主要文件和架构变化；
- 数据库迁移及回滚说明；
- 自动化测试命令与结果；
- 手工验收步骤；
- 安全、性能和兼容性影响；
- 已知限制和明确不在本阶段的内容；
- 下一阶段仅作预告，不在当前 PR 中实现。
