# 原生订单创建幂等重放

适用于 local/production 的 `POST /api/v2/sales/orders`、`POST /api/v2/procurement/orders`，截至 R5-L。确认和取消规则见 [原生订单动作](native-order-actions.md)。

## 创建与重试

创建继续要求当前组织有效成员的 `sales:create` / `procurement:create`。仅有创建权限的 SELF、DEPARTMENT 或 ASSIGNED 用户可以创建自己的草稿，重试不隐式要求 view、submit 或 ALL。创建响应包含其新建订单和行，这是创建操作的结果，不扩大详情读取范围。

幂等键按组织和操作隔离，去除两端空白。同组织、同操作已存在该键时，只有订单的原创建人可以得到当前订单及行；采购使用 `buyer_user_id`，销售使用 `sales_user_id`。不同创建人（包括有 ALL 查看权限的用户）得到 `409 IDEMPOTENCY_CONFLICT`，响应不附带原订单 ID 或明细，数据库行和幂等记录不改变。历史创建人为空或不能匹配当前用户时同样拒绝，不自动接管。需要创建另一订单时必须使用新键。

每次调用仍检查当前 create 权限和组织成员状态；既有会话撤权或成员停用后不能靠重放取回结果。详情读取继续独立检查 view 和行范围。

保留现有重试契约：成功重放返回订单当前状态和版本，确认或取消后不会重新创建草稿。同一文本键在采购和销售之间互不占用，另一组织不会选中当前组织的订单；双方争用同组织同操作的键时，数据库唯一声明只允许一个创建事务成功，另一方冲突后不能获取赢家订单。没有迁移或改写历史订单。

## 验证与边界

`TradeInventoryMySqlTest` 增加采购/销售各四组真实 MySQL 用例：本人重放与当前状态、他人键冲突、历史缺失创建人、两个创建人并发。`native-order-replay-smoke.ps1` 用 14 个 HTTP 场景检查 ALL/SELF/DEPARTMENT/ASSIGNED、仅创建、撤权、停用、组织隔离、操作隔离和归一化，负例比较 27 张表的排序后完整行，SQL 只读。脚本固定 API18080，且要求 DB_URL 明确为授权隔离库。

此批不新增请求正文指纹；原创建人复用同一键而更改正文仍沿用既有结果。请求正文一致性、来源单据和来源行的实际关联、其他原生动作、完整浏览器以及故障注入仍须独立验证，不能用此批结果宣称全部交易或 F27 已完成。
