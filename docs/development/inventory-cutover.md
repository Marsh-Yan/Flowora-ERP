# R2：履约与库存统一

兼容收货保存并刷新订单行后，关联 v2 流水到实际收货行，再按全部采购行决定 RECEIVED 或 PARTIALLY_RECEIVED；兼容发货保存实际出库行并关联 v2 流水，刷新销售订单行后按全部销售行决定完成状态。两者仍在原有事务中，保留已有审批和会计调用。`accepted_quantity` 已由 V13 创建，此阶段补齐实体映射，不修改 V13。

## 权威来源决策

在 `local` / `production` 环境，`flowora_inventory_balance_v2` 是唯一实时库存余额，`flowora_stock_movement` / `flowora_stock_movement_line` 是库存流水。仓库、商品汇总由 `flowora_inventory_summary_v2` 提供，compat/v1 列表、页面、分析与导出使用相同汇总。可用量扣除预留，冻结库存可用量为零。

`flowora_stock_balance`、`flowora_stock_ledger_entry` 保留为切换前历史。迁移后的业务不得再独立更新旧余额。无数据库的 standalone 演示继续使用原服务，不作为生产库存依据。

兼容表单只描述仓库、商品，无法表达库位、批次与序列号。其库存操作限定在空库位、无批次、无序列号的 `NONE` 跟踪商品；需要跟踪维度时使用原生 v2 接口，不能将整个仓库汇总强行写回单一维度。兼容操作保留已有单据、审批及会计契约，库存变动接入 v2 引擎。

## 履约状态矩阵

| 动作 | 允许状态 |
|---|---|
| 采购收货 | CONFIRMED、APPROVED（旧版已批准采购单）、PARTIALLY_RECEIVED |
| 销售预留、原生 v2 发货 | CONFIRMED、RESERVED、PARTIALLY_FULFILLED |
| 兼容直接发货 | CONFIRMED、PARTIALLY_FULFILLED；不得抢占已预留库存 |

草稿、取消、关闭、已全部履约及不在矩阵内的状态拒绝履约。操作先锁订单头，再检查行、预留和库存；取消也先锁同一订单头。数量、版本增长、状态、库存、流水与财务来源在同一事务内提交。取消仍使用客户端传入版本；履约使用锁内当前版本及数量约束，不接受脱离锁的状态检查。重新预留不能把部分履约状态退回 RESERVED。

## V17 历史切换与 V18 数量核对

升级前备份并停止全部业务写入实例。先运行 [差异查询](../../tools/sql/inventory-cutover-preflight.sql)，核对每个组织、仓库、商品的旧余额、v2 余额和已重复表达的来源。

V17 不修改 V1–V16，且不会盲目将旧余额再加一次：

1. 用组织、仓库、商品、来源类型和来源单据 ID 识别已在 v2 表达的旧流水；重叠流水必须数量和金额完全匹配。
2. 验证现存 v2 余额数量与其流水一致，避免将未记录的手工回填再当成缺失期初。
3. 导入差额 = 旧余额 - 已在 v2 表达的旧流水。完整重复来源导入零；部分已表达来源可能产生负向修正。
4. 将差额写入默认维度，重算其平均成本，记录 `flowora_inventory_cutover` 快照与 `OPENING / INVENTORY_CUTOVER` 流水。负向修正不得占用预留库存。
5. Flyway 只执行一次。再次启动或迁移不会再次导入。

V18 在切换后对余额与流水做双向数量核对，覆盖“流水存在但余额行缺失”的异常；存在差异时停止迁移和启动。V17 已在隔离演练中应用，因此该补充校验使用新增 V18，不重写 V17。

发现重叠流水不一致、无流水支持的 v2 余额、需要跨维度调整、零数量但非零估值或不合法的负向修正时，迁移报错并回滚数据变更。服务不得带着猜测库存启动。应根据报错和差异查询人工核对，保留备份和调整依据；MySQL DDL 非事务性，失败可能保留新建视图、快照表或过程，应在维护窗口核查残留结构及 Flyway 失败记录后恢复或修复，不能直接重新加库存。

统一流水包含 v2 历史及切换修正，切换前旧明细仍留在归档表。切换修正记录在切换时刻；切换前 v2 流水的运行余额可能尚未包含旧库存，不能用它代替切换前历史报表。当前余额和切换后的流水应一致；移动平均成本采用数据库四位小数精度，价值汇总可能存在相应舍入尾差。

## Demo 初始化

demo 脚本在 Flyway 后同时初始化 v2 余额和期初流水：16 件，单位成本 40，价值 640。reset 先清理 demo 组织的 v2 库存、流水及切换快照再初始化，重复执行仍只有一份期初库存。生产环境禁止启动 demo seed。

## 验证

常规：`pnpm verify:web` 与 `./mvnw -B -pl services/api -am test package`。

真实 MySQL 回归为显式启用测试，URL 仅允许 `jdbc:mysql://127.0.0.1:13306/audit_flowora?...`：设置 `FLOWORA_R2_MYSQL_URL`、可选 `FLOWORA_R2_MYSQL_PASSWORD` 后运行 `./mvnw -B -pl services/api -Dtest=TradeInventoryMySqlTest test`。测试为每次执行创建独立测试组织，并只删除该组织的测试记录。

CI 的 Inventory MySQL regression 使用临时空数据库，额外设置 `FLOWORA_R2_EMPTY_CI_DATABASE=true`，先迁移至 V16 并构造缺失期初、部分重复、全部重复的历史样本，再升级 V17；验证再次迁移和两次 demo 初始化不会重复加库存。该开关在非空库中直接失败，不可用于已有数据环境。

回归覆盖非法状态无副作用、超量及错误仓库回滚、分批/全部收发、退货、调拨、盘点与取消并发竞争。R3 财务整改仍按独立阶段推进。

HTTP 回归脚本 [compat-stock-smoke.ps1](../../tools/verification/compat-stock-smoke.ps1) 只允许 `http://127.0.0.1:18080` 的隔离 API，依赖 demo 测试资源。设置 `FLOWORA_R2_HTTP_PASSWORD` 后运行；可用 `-Username` 指定合成测试账号。脚本创建多行采购/销售单据，验证草稿拒绝无履约和流水变化、逐行收发的整单状态、来源行关联、原生退货、余额口径及完整导出数量集合，最后注销会话。不可在业务数据库上运行。
