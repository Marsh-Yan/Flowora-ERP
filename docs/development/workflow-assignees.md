# 兼容工作流显式指派与转派资格（R5-H，2026-10-02）

`/api/v2/compat/workflow` 创建任务的显式 `assigneeUserId` 和 OPEN 任务的 `transferToUserId` 使用同一服务端资格规则。在保存任务、通知、活动、审计及评论之前验证，不以角色名称或调用方的管理员身份替代目标资格，不给目标添加成员关系、角色、权限或业务数据范围。

目标账户必须为 ACTIVE、active=true 且当前未锁定；在任务所在组织具有有效成员关系，组织也须有效。实时读取该组织的成员角色与权限，不读取目标旧登录会话，也不按用户的默认组织判断归属。因此拥有多个组织成员关系的用户，只要本组织资格有效仍可被指派。

| 任务状态 | 目标权限 |
| --- | --- |
| 需要审批的 OPEN 任务，以及转派 | `workflow:view`，并具备 `workflow:approve` 或 `workflow:delegate` |
| 自动批准的任务，显式指派后负责 COMPLETE | `workflow:view` + `workflow:submit` |

仅有 delegate 的目标可以继续转派，但不能审批；仅有 workflow:admin 不等于具备审批或转派资格。动作调用方仍使用已有细分权限、当前受派关系、任务状态及附带评论权限规则。

目标还必须能够读取来源资源：沿用 `WorkflowResourceAccessPolicy`、采购/销售订单及项目的现有行范围。合法 SELF 来源所有者可以接收自己的任务；不能利用指派把他人的订单加入 SELF，也不能把不支持订单读取的 ASSIGNED 范围扩大为 ALL。GENERAL 沿用 workflow:view，仍不是数据库资源。其他不支持的范围继续拒绝，不自动放宽。

不存在、跨组织、停用/锁定、成员无效、权限不足和来源越界统一返回 409 `WORKFLOW_ASSIGNEE_INVALID`，中英文提示要求选择有效成员，不暴露目标存在性或具体权限/来源信息。空转派 ID 仍由原状态校验拒绝。数据库或服务故障不伪装为目标无资格，仍作为服务错误处理；资格策略不可用时不能静默允许显式指派。默认 standalone 仅提供诊断，不作为数据库业务资格验证环境。

没有新迁移，不批量改写旧任务。历史不合格指派需单独清点；有效管理员仍须具备 workflow:admin 与 workflow:delegate 才能替换不合格处理人。旧角色池指派（未给 assigneeUserId）和原生 v2 模板/实例的独立解析模型不在本阶段改动范围。资格校验只证明当前请求观察到的有效状态，不宣称撤权与转派提交的所有并发顺序均已验证。

`tools/verification/workflow-transfer-smoke.ps1` 18场景在真实隔离MySQL/HTTP验证不存在、跨组织、停用、成员停用、锁定、角色停用、权限与范围实时撤销、SELF/ASSIGNED越界、缺少来源/工作流查看权限，以及合法审批、仅转派链路、多组织成员和SELF所有者。负向目标同时验证转派及显式创建，SQL只读对照任务状态、受派者、version、通知、活动、审计、评论及任务数量。正向还验证恰好一条转派通知、原处理人不能继续转派、接收人能实际审批或继续分派，以及自动批准任务的合法完成。
